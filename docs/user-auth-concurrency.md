# 회원정보와 인증 토큰의 동시 갱신 (#97)

## 원인

User 엔티티의 기본 UPDATE에는 변경하지 않은 refresh_token도 포함된다. 닉네임/알림 설정 수정이 잠금 없이 사용자를 읽으면, 다른 요청이 재발급하거나 로그아웃한 뒤 예전 토큰을 다시 저장할 수 있었다.

## 갱신 규칙

- 닉네임 수정, 알림 설정 변경, 탈퇴는 트랜잭션의 첫 사용자 조회에 findByIdForUpdate를 사용한다.
- 로그인은 findByGoogleSubForUpdate, refresh/logout은 findByIdForUpdate로 같은 사용자 행에 쓰기 잠금을 건다.
- 기존 방문/좋아요/리뷰 생성과 같이 사용자 행을 먼저 잠그고 관련 데이터를 처리한다.
- 탈퇴는 사용자 잠금 후 Review -> Like -> Visit -> User 순서로 삭제한다.
- 내 정보/알림 설정 조회는 읽기 전용 findById를 유지한다.
- 기존 사용자 객체를 다른 트랜잭션에서 전달하거나, 일반 조회로 먼저 영속성 컨텍스트에 적재한 후 쓰기 서비스에 넘기는 경로를 추가하지 않는다. 행 잠금만으로 이미 적재된 오래된 엔티티가 자동 갱신되는 것은 아니다.
- 신규 가입은 아직 존재하지 않는 행을 생성하는 별도 흐름이다. 동시 가입 제약 오류 처리는 #97 범위에 포함하지 않는다.

## API

요청/응답 스키마 변경 없음. 다른 사용자 요청의 영향을 받지 않으며, 같은 사용자의 변경 요청은 앞선 트랜잭션 종료까지 기다린다. 없는/탈퇴한 사용자의 수정은 기존 UnauthorizedException(401), refresh는 InvalidRefreshTokenException(401)이다.

## 검증

UserAuthConcurrencyTest는 별도 스레드/트랜잭션으로 다음을 확인한다.

- 닉네임/알림 설정과 refresh/logout의 8개 실행 순서 조합.
- 로그아웃 후 토큰 null 유지, 사용된 refreshToken 재사용 거절, 회전된 토큰으로 재발급 성공.
- 닉네임과 알림 설정을 함께 변경해도 양쪽 값 보존.
- 탈퇴를 기다리는 수정 요청은 401에 해당하는 예외를 내고 사용자를 복구하지 않음.

기존 MySQL CI의 TEST_REQUIRE_MYSQL=true 환경에서는 테스트 시작 시 실제 DB 제품이 MySQL인지 검증한다. 로컬 H2 통과를 MySQL 검증 완료로 간주하지 않는다. 실제 MySQL CI 결과를 확인한 뒤 이슈의 MySQL 검증 항목을 완료 처리한다.

스키마 변경이나 운영 데이터 보정은 필요하지 않다. 기존에 유출되거나 복구된 토큰의 일괄 폐기는 별도 운영 판단이며 이번 변경에서 실행하지 않는다.
