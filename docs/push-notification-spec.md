# 방문 중 대체 장소 백그라운드 푸시 (이슈 #89)

프론트가 앱을 띄워 `POST /api/visits/{visitId}/alternative-suggestion/check`를 직접 호출하지 않아도,
서버가 주기적으로 진행 중(STARTED) 방문을 평가해 고요지수가 하락하면 FCM으로 알림을 보낸다.
판정 로직(절대 40점 미만/상대 15점 이상 하락)과 대체지 계산은 기존 `NudgeStore`/`AlternativeService`를 그대로 재사용한다 — 새 로직을 따로 만들지 않는다.

## 1단계 범위 (이번에 구현한 것)

- FCM 연동 (Firebase Admin SDK), 자격증명 미설정 시 자동 비활성화
- 기기 토큰 등록/해제 API
- 로그아웃 직전 해제, 탈퇴 시 일괄 정리
- 진행 중 방문 백그라운드 평가 스케줄러 (기존 nudge 판정 재사용)
- 같은 제안에 대한 중복 발송 방지
- 무효 토큰(UNREGISTERED) 자동 정리

**2단계로 미룬 것** (필요해지면 별도 이슈로): 발송 실패 재시도 큐, 다중 기기 발송 정책 세분화(현재는 사용자의 모든 등록 기기에 동일 발송), 알림 클릭 딥링크 프론트 연동.

## FCM 설정

```
fcm:
  credentials-path: ${FCM_CREDENTIALS_PATH:}
```

Firebase 콘솔 → 프로젝트 설정 → 서비스 계정 → **새 비공개 키 생성**으로 받은 JSON 파일을 서버에 올리고,
그 경로를 `FCM_CREDENTIALS_PATH` 환경변수로 지정한다. **git에 올리지 않는다.**

값이 비어있으면 앱은 정상 기동하고 다른 기능도 그대로 동작하지만, 백그라운드 평가에서 트리거가 발생해도
푸시는 발송되지 않고 로그(`FCM 미설정으로 푸시 발송을 건너뜁니다`)만 남는다 — 운영 반영 전 단계적 배포가 가능하다.

## 기기 토큰 API

### `POST /api/users/me/device-tokens`

```json
{ "token": "fcm-device-token" }
```

로그인 직후, 그리고 OS가 토큰을 갱신해줄 때마다(APNs/FCM 토큰 갱신 콜백) 호출한다.
같은 토큰으로 다른 계정이 다시 등록하면(기기 재사용, 로그아웃 없이 다른 계정으로 전환 등) 소유자가 그 계정으로 넘어간다 — 이전 계정에는 더 이상 발송되지 않는다.

### `DELETE /api/users/me/device-tokens`

```json
{ "token": "fcm-device-token" }
```

**로그아웃 직전에 프론트가 호출**한다. 기존 `POST /api/auth/logout`(리프레시 토큰 무효화)과는 별개 책임이라 의도적으로 분리했다 — 로그아웃 API 자체에 토큰 파라미터를 얹지 않는다.
본인 소유가 아니거나 이미 없는 토큰이면 조용히 무시한다(멱등, 에러 아님).

탈퇴(`DELETE /api/users/me`) 시에는 사용자의 모든 기기 토큰이 서버에서 일괄 삭제된다 — 프론트가 별도로 호출할 필요 없다.

## 백그라운드 평가

```
visit:
  nudge:
    background-interval-ms: 120000  # 2분, 잠정값
```

매 주기마다 `alternative_notification_enabled = true`인 사용자의 STARTED 방문을 모두 조회해
기존 `NudgeStore.prepare`/`publish` 흐름(= `/check` API와 동일한 로직)을 그대로 돌린다.
AI 호출 실패, 방문 하나의 처리 실패는 그 건만 로그로 남기고 나머지 방문 평가를 막지 않는다.

**주기 2분은 잠정값이다.** AI 호출 비용(진행 중 방문 수만큼 `/alternative` 호출 발생)과 알림 체감 지연을 운영에서 보고 조정 필요 — 이슈 #89에 남겨둔 채 확정 안 됨.

## 중복 발송 방지

`visit.alternative_notified_at` 컬럼이 "지금 저장된 제안(issuedAt)에 대해 이미 알렸는지"를 기록한다.
같은 제안이 만료 전까지 매 주기 계속 평가돼도(TTL 10분, `visit.nudge.proposal-ttl`) 한 번만 발송한다.
제안이 만료되고 새로 트리거되면 issuedAt이 갱신되므로 자연스럽게 재발송된다.

## 푸시 payload

```json
{
  "notification": { "title": "더 한적한 곳이 있어요", "body": "..." },
  "data": { "type": "ALTERNATIVE_SUGGESTION", "visitId": "123" }
}
```

전체 제안 내용(대체지 목록 등)은 payload에 담지 않는다. **알림을 클릭하면 프론트가 `visitId`로
`GET /api/visits/current` 또는 `/check`를 다시 호출해 현재 방문 상태를 복원**하도록 한다 — 완료 기준의
"알림 클릭 후 현재 방문 상태를 재조회해 화면을 복원한다"와 동일.

## 발송 실패 처리

- FCM이 `UNREGISTERED`(기기에서 앱 삭제/토큰 만료)를 반환하면 해당 기기 토큰을 즉시 삭제한다.
- 그 외 오류는 로그만 남기고 다음 주기에 다시 시도된다 — 별도 재시도 큐는 없다(1단계 범위 밖).
- 푸시 발송 실패가 방문 완료/취소 등 핵심 흐름에 영향을 주지 않는다 — 완전히 분리된 스케줄러 경로다.

## 전달 보장에 대한 한계 (완료 기준 참고사항)

- **FCM 접수 성공과 실제 기기 수신 성공은 다르다.** `client.send()`가 예외 없이 끝나도 실제로 기기가
  받는다는 보장은 아니다(네트워크 상태, OS 배터리 최적화 등).
- **OS가 앱 프로세스를 강제 종료한 상태**(일부 제조사의 공격적인 백그라운드 종료 정책 등)에서는 FCM이
  접수해도 알림이 지연되거나 아예 전달되지 않을 수 있다. 이는 서버가 통제할 수 없는 영역이다.
- 위 두 가지는 서버 로그의 "발송 성공"이 곧 "사용자가 알림을 봤다"를 의미하지 않는다는 뜻이다.

## 남은 것 (2단계 이후)

- 프론트: 알림 권한 요청, 알림 수신 시 딥링크 처리, 앱 재진입 시 방문 화면 복원
- 발송 실패 재시도 정책 (지수 백오프 등)
- 다중 기기 발송 세분화(예: 최근 활성 기기만 등)
